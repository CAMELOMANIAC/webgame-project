# 개발·검증 절차

## 환경

패키지 관리자는 pnpm 9를 사용한다. 현재 검증 환경은 Node.js 24.16.0, pnpm 9.0.0이다. 개발 서버의 `--env-file` 옵션을 지원하는 Node.js가 필요하다.

## 최초 준비

1. 저장소 루트에서 `pnpm install`을 실행한다. 공통 타입 패키지 빌드도 함께 실행된다.
2. `apps/server/.env.example`을 참고해 `apps/server/.env`를 준비한다. 기존 연결 설정은 덮어쓰지 않고 값은 외부에 공개하지 않는다.
3. `DATABASE_URL`과 `DIRECT_URL`을 개발용 PostgreSQL(또는 Supabase 연결 문자열)로 설정한다.
4. 새로 만든 일회용 개발 데이터베이스에 한해 `pnpm --filter server db:push`로 Drizzle 스키마를 반영한다. 기존 데이터베이스에 적용하려면 변경 내용을 먼저 확인한다.

데이터베이스 스키마와 관계는 `apps/server/src/db/schema.ts`에서 단일 원본으로 관리하며, `apps/server/drizzle.config.ts`를 통해 `drizzle-kit`과 연동한다. Supabase Transaction Pooler 환경에서도 동작하도록 `postgres` 드라이버의 `prepare: false` 설정을 기본 적용한다. 새 빈 DB의 로컬 준비 명령은 [README](../README.md)에 있다.

현재 사용자의 선택에 따라 기존 외부 데이터베이스에는 적용하지 않았다. 새 코드를 기존 연결로 실행하면 탐사·개체·임무 컬럼이 없다는 오류가 날 수 있다. 검증 시에는 새 스키마를 적용한 별도 로컬 테스트 DB를 명시적으로 사용한다.

새 빈 개발 DB에는 `pnpm --filter server db:push`를 사용한다. 이미 기존 테이블이 있는 DB는 먼저 스키마 변경 내역을 확인한 뒤 반영해야 하며, 확인 없이 초기화나 시드를 실행하지 않는다. 외부 DB 적용은 별도 사용자 승인 후 진행한다.

기존 DB에서 세계선 코드만 제거할 때는 다음 SQL을 사용한다. PostgreSQL은 컬럼을 삭제할 때 해당 컬럼을 포함한 중복 방지 인덱스도 함께 삭제한다.

```sql
BEGIN;
ALTER TABLE "CharacterVariant" DROP COLUMN IF EXISTS "worldlineCode";
ALTER TABLE "GhostSnapshot" DROP COLUMN IF EXISTS "worldlineCode";
COMMIT;
```

## 개발 실행

루트에서 `pnpm dev`를 실행한다. 공통 타입 감시 빌드, 게임 화면, API 서버가 실행된다.

- 게임: Vite가 표시하는 로컬 주소. 거점 홈은 `/#/base`, 탐사 중 거점 미리보기는 `/#/field/user`이다.
- 첫 화면에서 개발용 계정을 선택하며, 상단의 계정 변경으로 전환한다. 고정 사용자 ID는 사용하지 않는다.
- API: `http://localhost:3001`.
- API 생존 확인: `GET /health`. 데이터베이스 연결 성공을 보장하는 주소는 아니다.
- 게임 연결 대상: `VITE_API_BASE_URL`. 미지정 시 `http://localhost:3001`을 사용한다.

## 검증 명령

모두 저장소 루트에서 실행한다.

```sh
pnpm check-types
pnpm lint
pnpm test
pnpm build
```

`check-types`는 게임·서버·공통 타입·공통 UI의 타입을 검사한다. 빌드 결과물을 갱신하는 명령은 아니다.

`test`는 실제 포트를 열거나 데이터베이스에 접속하지 않고 서버 API를 검증한다. 서버는 `buildApp({ database, logger })`로 생성하며, 테스트에서 데이터베이스 클라이언트를 주입할 수 있다. 별도 테스트 데이터베이스를 연결할 때는 운영용 연결과 분리한다.

실제 아이템 트랜잭션 검증은 `TEST_DATABASE_URL`을 별도로 지정하고 `pnpm --filter server test:integration`을 실행한다. 이 명령은 기존 `.env`를 읽지 않으며, 로컬 주소의 `webgame_test_*` 데이터베이스만 허용한다. 테스트는 직접 생성한 사용자·캐릭터·아이템만 정리한다. 검사 전에 해당 테스트 DB에 현재 Drizzle 스키마(`pnpm --filter server db:push`)를 반영해야 한다.

예를 들어 일회용 PostgreSQL을 `127.0.0.1:55432`에 실행하고 `webgame_test_inventory` 데이터베이스를 준비해 검증할 수 있다. 기존 개발·운영 연결 문자열을 테스트용으로 사용하지 않는다.

`build`는 공통 타입을 먼저 빌드하고 게임과 서버를 생성한다. 서버는 공유 소스도 컴파일하므로 시작 파일은 `apps/server/dist/apps/server/src/index.js`에 생성된다.

빌드된 서버를 실행할 때 환경변수를 외부에서 설정한 뒤 다음 명령을 사용한다.

```sh
pnpm --filter server start
```

로컬 `.env`를 사용해 빌드된 서버를 확인할 때는 다음 명령을 사용한다.

```sh
pnpm --filter server exec node --env-file=.env dist/apps/server/src/index.js
```

## 테스트 데이터

현재 시드는 기존 캐릭터·장비·창고·고스트 등을 삭제하고 테스트 데이터를 다시 만든다. 평소 실행이나 검증에서는 실행하지 않는다.

일회용 테스트 데이터베이스에서 재생성하기로 판단한 경우에만 `pnpm --filter server db:seed`를 실행한다.

개발용 계정 선택은 `X-Dev-User-Id` 헤더를 사용한다. 실제 로그인은 아니며 `NODE_ENV=production`에서는 계정 선택과 개발 전용 API를 비활성화하고 개인 데이터 요청을 거부한다. 실제 인증 연결은 후속 작업이다.

탐사 이동·전투·탈출 요청에는 탐사 ID, 예상 상태 버전, 고유 요청 ID를 보낸다. 같은 요청을 재시도하면 저장된 결과를 반환하며 보상을 다시 지급하지 않는다. 라운드는 이동 간선당 1, 별도 전투 행동당 1 증가한다. 탐사마다 고스트 경로를 최대 3개 추적하며, 같은 라운드에 같은 노드에 도착하거나 같은 도로를 역방향으로 통과하면 조우한다. 최대 7일 이내의 기록을 사용한다.

이동 요청은 계정·캐릭터별로 브라우저 세션에 보관한다. 이동 중 새로고침하거나 응답을 받지 못하면 필드의 ‘이동 결과 다시 확인’으로 같은 요청을 재시도한다. 전투 기록은 재생 완료 후 미확인 요청에서 제거된다. 이전 계정의 늦은 응답과 이전 상태 버전이 현재 탐사를 덮어쓰지 않게 한다.

브라우저 검증용 서버는 `TEST_DATABASE_URL`을 설정하고 `pnpm --filter server preview:test`로 실행할 수 있다. 로컬 테스트 DB에만 임시 계정 2개와 장비를 추가하며, 다른 계정의 탐사에 시설 26과 도착 라운드가 일치하는 고스트 검증 기록을 준비한다. 별도로 게임 개발 서버를 실행해 ‘로컬 검증 생존자’를 선택한다. 정상 종료 시 생성한 데이터만 정리하며, 프로세스를 강제 종료했다면 일회용 DB 컨테이너를 정리한다.

첫 임무는 임무 통신 → 수락 → 창고 장비 장착 → 배치 → 임무 시설 이동 → 전투 → 탈출 → 보고 순서다. 개발용 개체 추가에서는 같은 인물의 변주도 반복 추가할 수 있다. 다른 개체를 선택하려면 진행 중 탐사와 미확인 전투 결과를 마쳐야 한다.

지도 원본은 `packages/types/src/assets/map_graph.json` 하나이며 서버·화면·경로 탐색·테스트가 같은 파일을 읽는다. 인물·세계선·아이템·중첩 규칙·임무의 구체적 명칭과 수치는 기획 제안으로 관리한다.

오너의 후기 공개 단계는 서버 응답 필터와 테스트로만 준비했다. 현재 첫 임무는 연구 기록 1개를 공개하며 오너를 언급하지 않는다. 공개되지 않은 인물의 내부 개체 ID는 API에서 보내지 않는다.

## 확인된 주의 사항

- 서버 소스 린트 경고는 해소했다. ESLint 설정 파일의 모듈 형식 안내는 남아 있다.
- 게임 배포 빌드에 큰 묶음 파일 경고가 있다. 지도 데이터와 그리기 라이브러리 등이 포함되므로, 동작과 측정 결과를 확인한 후 분할을 검토한다.
- 타입 검사·빌드·`/health`가 성공해도 데이터베이스에 연결한 탐사 한 사이클의 검증은 별도로 필요하다.
